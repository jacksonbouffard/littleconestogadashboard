Web Mapping Tool Update System

Architecture: Client-Side Tool → Google Form → Google Sheet + Apps Script → Google Drive

Purpose: Implement an authoritative update system where map edits are reviewed and approved before becoming official.

System Overview

┌─────────────────────────────────────────────────────────────┐ │ SYSTEM ARCHITECTURE │ ├─────────────────────────────────────────────────────────────┤ │ Web Map Tool → Google Form → Sheet + Scripts → Drive Files │ │ (GitHub Pages) (Collector) (Processor) (Storage) │ └─────────────────────────────────────────────────────────────┘
This system requires no backend infrastructure while maintaining authoritative control over data updates. All processing happens through Google's free services.
PHASE 1: User Submission Flow

User Interaction Process

USER OPENS WEB MAPPING TOOL │ ├→ Uploads file from Google Drive (manual download/upload) │ └→ System stores original state + version number │ ├→ Makes edits to map features │ └→ Each edit tracked as delta in background array │ └→ Clicks "Submit Changes for Review" │ ├→ Downloads pending file locally │ (Complete backup with changes) │ └→ Opens pre-filled Google Form │ ├→ Session ID (auto-filled, hidden) ├→ Base Version (auto-filled, hidden) ├→ Change Data JSON (auto-filled, hidden) └→ Notes (user can add comments) │ └→ User clicks Submit
Key Implementation Details:
  • Delta tracking captures only changes, not entire file
  • Session ID generated from timestamp + random string
  • Google Form opened with pre-filled data via URL parameters
  • User retains local backup of their complete changes
PHASE 2: Data Reception & Storage

Automated Data Collection

GOOGLE FORM SUBMISSION │ └→ Auto-populates Google Sheet row: │ ├→ Column A: Timestamp (automatic) ├→ Column B: Session ID ├→ Column C: Base Version ├→ Column D: Changes (JSON string) ├→ Column E: User Notes ├→ Column F: Status (empty, awaiting) ├→ Column G: Approval Time (empty) └→ Column H: Conflict Flag (formula) │ └→ Trigger: onFormSubmit() │ ├→ Sets Status = "PENDING" ├→ Checks version conflicts └→ [Optional] Email notification
PHASE 3: Review Interface

Administrative Control Panel

GOOGLE SHEET with CUSTOM MENU │ └→ "Map Updates" Menu (via Apps Script) │ ├→ "Review Selected Row" │ └→ Shows changes in sidebar │ ├→ Session info │ ├→ Change count │ └→ Detailed delta view │ ├→ "Check for Conflicts" │ └→ Compares against current version │ ├→ No conflict → Green flag │ └→ Conflict → Shows differences │ └→ "Approve Selected Row" └→ [Continue to Phase 4]
PHASE 4: Automated Merge Process

Approval & File Management

APPROVE BUTTON CLICKED │ ├→ Validates submission │ ├→ Check: Valid JSON? │ ├→ Check: Version exists? │ └→ Check: User already processed? │ ├→ Retrieves current file from Drive │ └→ Folder: /Shared Map Data/ │ └→ File: map_data_current.js │ ├→ Applies deltas sequentially │ ├→ For each change in submission: │ │ ├→ Type: "modify" → Update feature │ │ ├→ Type: "add" → Insert feature │ │ └→ Type: "delete" → Remove feature │ └→ Error handling: │ ├→ Missing feature → Log & skip │ └→ Duplicate ID → Generate new ID │ ├→ Archives current version │ └→ Copies to: /archive/map_data_v[X.X].js │ ├→ Saves new version │ ├→ Increments version number │ ├→ Updates: map_data_current.js │ └→ Adds metadata (version, timestamp) │ └→ Updates tracking files ├→ version_manifest.json │ ├→ current_version: "1.2.3" │ ├→ last_updated: ISO timestamp │ ├→ changes_applied: count │ └→ pending_reviews: count │ └→ Sheet row updates: ├→ Status → "APPROVED" ├→ Approval Time → Now └→ New Version → "1.2.3"
PHASE 5: Conflict Resolution

Handling Concurrent Edits

MULTIPLE PENDING SUBMISSIONS │ ├→ First submission (User A, Base v1.0) │ └→ No conflict → Approve → Creates v1.1 │ └→ Second submission (User B, Base v1.0) └→ VERSION CONFLICT DETECTED │ ├→ Option 1: Auto-Rebase │ ├→ Check if changes overlap │ ├→ No overlap → Apply to v1.1 │ └→ Creates v1.2 │ ├→ Option 2: Manual Review │ ├→ Show both changesets │ ├→ Admin selects changes │ └→ Custom merge → v1.2 │ └→ Option 3: Reject ├→ Mark as "NEEDS RESUBMISSION" └→ User must update to v1.1 first
Since users typically edit different features, most conflicts can be automatically resolved by applying non-overlapping changes sequentially.
PHASE 6: Distribution & Updates

Version Distribution System

NEW VERSION PUBLISHED │ ├→ Google Drive Structure: │ /Shared Map Data/ │ ├→ map_data_current.js (v1.2) │ ├→ version_manifest.json │ └→ /archive/ │ ├→ map_data_v1.0.js │ └→ map_data_v1.1.js │ └→ Next User Session: │ ├→ User opens web tool ├→ Tool fetches version_manifest.json ├→ Compares versions └→ If outdated: ├→ Shows warning banner ├→ "Download Latest Version" └→ Links to Drive folder

Google Apps Script Components

Required Script Functions:

  • Menu & UI Functions:
    • onOpen() - Creates custom menu in Sheet
    • reviewChanges() - Displays changes in sidebar
    • showConflicts() - Analyzes version conflicts
  • Processing Functions:
    • approveChanges() - Main approval handler
    • mergeDeltasToMaster() - Applies all changes
    • applyDelta() - Processes individual change
    • validateSubmission() - Pre-approval checks
  • File Operations:
    • getCurrentFile() - Reads from Drive
    • saveNewVersion() - Writes updated file
    • archiveVersion() - Backs up old versions
    • updateManifest() - Updates version metadata
  • Automated Triggers:
    • onFormSubmit() - Processes new submissions
    • dailyCleanup() - Archives old pending items

Status Code Definitions:

  • PENDING - Awaiting review
  • APPROVED - Successfully merged
  • CONFLICT - Version mismatch detected
  • ERROR - Processing failed
  • REJECTED - Manually declined
  • RESUBMIT - Needs update to latest version

Implementation Steps

Step 1: Create Google Form

  1. Create new Google Form with required fields
  2. Get pre-fill URL and extract entry IDs
  3. Link form to new Google Sheet

Step 2: Set Up Google Apps Script

  1. Open Sheet → Extensions → Apps Script
  2. Copy provided script functions
  3. Update configuration with Drive folder ID
  4. Run initial authorization

Step 3: Configure Web Tool

  1. Add delta tracking to existing edit functions
  2. Implement form submission with pre-filled URLs
  3. Add version checking on load
  4. Create user feedback for submission status

Step 4: Test & Deploy

  1. Test with sample edits
  2. Verify approval process
  3. Check version increment and archiving
  4. Train users on new workflow

Error Handling

ERROR SCENARIOS │ ├→ Malformed JSON in submission │ ├→ Status → "ERROR" │ ├→ Log error details │ └→ [Optional] Email admin │ ├→ Drive permission issues │ ├→ Retry with exponential backoff │ └→ Alert admin after 3 failures │ ├→ Version file missing │ ├→ Create new from latest archive │ └→ Reset version numbering │ └→ Concurrent approvals ├→ Script lock (prevents race conditions) └→ Queue processing

Benefits of This System

  • No Backend Required: Entirely runs on free Google services
  • Authoritative Control: Only approved changes become official
  • Complete Audit Trail: Every change tracked with timestamp and session
  • Conflict Prevention: Version checking prevents data loss
  • User-Friendly: Simple interface for non-technical users
  • Automatic Archiving: Full version history maintained
  • Scalable: Can handle multiple concurrent users

Maintenance Requirements

Regular Tasks:
  • Daily: Review and approve pending submissions
  • Weekly: Check for failed submissions or errors
  • Monthly: Archive old versions to separate storage
  • As Needed: Resolve version conflicts manually
This system design minimizes manual intervention while maintaining complete control over data integrity. Most operations are automated through Apps Script, requiring only approval clicks for valid submissions.
